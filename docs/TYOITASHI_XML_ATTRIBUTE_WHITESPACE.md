# XML属性の改行とタブを保つ

カットインのテキストレイヤーに複数行の文を入れて複製すると、改行が空白に変わっていた。保存して読み込んでも同じことが起きる。P2Pの同期では残る。XMLを通る経路だけの不具合なので、属性値の書き出し方を直した。

## 原因

`ObjectSerializer.toXml()` は属性値を `&` `<` `>` `"` `'` だけエスケープし、改行（LF・CR）とタブはそのまま書いていた。XMLの仕様では、パーサーは属性値の中に生で現れた改行とタブを空白1文字に置き換える（属性値の正規化）。Chromium の `DOMParser` では改行とタブすべて、happy-dom ではLFについて、この置き換えを確認した。`&#10;` のような文字参照で書かれていれば、置き換えは起きず元の文字に戻る。

`CutInLayer.text` は ObjectNode の属性として保存され、複製（`clone()`）もいったんXMLへ書き出してから読み直して作るので、ルームを保存しなくても、複製しただけで改行が消えていた。

## 基点と範囲

- 基点：`75b16b3a52adfe214953e9b995872b6d1096f18e`（`codex/xml-attribute-line-breaks` の分岐元）
- 変更：`src/app/core/sync/object-serializer.ts` に属性値用の `encodeAttributeValue()` を足し、`toXml()` の属性だけをこれで書く。通常のエスケープをかけたあと、タブ・LF・CRを `&#9;`・`&#10;`・`&#13;` に置き換える。
- 触っていないもの：要素の本文（`innerXml()`、チャット本文など）の書き方、`encodeEntityReference()` と `decodeEntityReference()`、読み込み側の `parseAttributes()`、XMLの形式とスキーマ、P2Pの同期。

## 互換性

- 改行もタブも含まない属性は、これまでとまったく同じ文字列で書き出す。差分が出るのは、属性値に改行かタブがある場合だけ。
- 新しい形式で保存したデータを古い版で開くと、文字参照はパーサーが解いてくれるので、改行が戻る。古い版にとっても読める形式のまま。
- 古い版で保存したデータの改行は、保存した時点ですでにファイルの中で生の改行になっている。読み込むと従来どおり空白になり、この変更では取り戻せない。
- 保存時の整形（`formatXml()`）はタグを1つのトークンとしてそのまま扱うので、属性の中の文字参照は崩れない。

## テスト

`src/app/core/sync/object-serializer.spec.ts` に次を足した。

- 属性のCR・LF・CRLF・タブが文字参照で書き出され、XML全体に生の改行とタブが残らないこと
- 改行のない普通の属性は従来どおりの文字列になり、`&#` を含まないこと
- 要素の本文に含まれる改行とタブは、これまでどおりそのまま書かれること
- LF、CR、CRLF、タブ、両端の改行、引用符と `&`、日本語と絵文字を含む値が、書き出しと読み込みで元に戻ること
- 改行を含む `CutInLayer.text` が `clone()` のあとも同じ値になること
- 以前の形式で保存された1行のテキストレイヤー（`&amp;` と `&quot;` を含む）が、従来どおり読めること
- 以前の形式で属性に生の改行があると空白として読まれること（既知の挙動を固定するテスト）

修正を外して流すと、このうち6件が落ちる。happy-dom はLFを空白にするが、CRとタブはそのまま残すため、CRとタブの往復テストは修正前でも通る。そこで、Chromium の挙動は別に確かめた。

- 手元の Playwright（Chromium 153）で、修正前と修正後の書き方で作った属性を `DOMParser`（`application/xml`）に読ませた。修正前はLF・CR・CRLF・タブがすべて空白になり、修正後は8種類の値がすべて元どおりに戻った。この確認用のスクリプトはリポジトリに含めていない。
- `npx vitest run`（対象4ファイル、132件）、`ng test --include`（対象3ファイル、80件）、`tsc`（app と spec）、変更ファイルへの `eslint` と `prettier --check`、`npm run build` が通った。

## 制限と、別に見つかった問題

- 属性の読み込みは、DOMがすでに参照を解いた値に、もう一度 `decodeEntityReference()` をかけている。そのため、利用者が `&amp;` や `&#10;` という文字列そのものを属性に入れると、読み込み後に `&` や改行に化ける。この二重デコードは修正前からある。今回は手を入れていない。直すと古いセーブの読み方が変わるおそれもあり、扱うなら別の変更で検討する。
- 属性値にタブ・改行・CR以外の制御文字があっても、扱いは変わらない。これらはXML 1.0では書けず、読み込み時の `sanitizeXml()` が取り除く。
- 保存時の整形は要素本文の前後の空白を削る。これも以前からの挙動で、今回は扱っていない。
